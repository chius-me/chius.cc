# HomeLab 降功耗文章去 AI 味改写设计

## 目标

把现有《给两台 PVE 主机降功耗：一次 HomeLab 节能优化实录》重写为一篇第一人称技术日记。文章应当像作者在现场一边关机器、一边看 UPS、一边修正判断后写下的记录，而不是事后生成的一份标准教程。

## 标题

改为《给 HomeLab 降降功耗》。标题只交代这次折腾的主题，不使用“实录”“指南”“最佳实践”等教程式包装。

## 参考风格

参考 lyc8503.net 的 HomeLab 与 Linux 排障文章所呈现的表达特征，但不复制其句子、固定口头禅或标点习惯：

- 从具体问题和个人动机写起，不先提出方法论。
- 保留尝试失败、判断变化、暂时解释不了的现象。
- 技术细节直接跟在事情发生的位置，不集中包装成知识点。
- 允许吐槽、括号和长短不一的段落，但不为了“像真人”刻意制造错别字或粗口。
- 结尾写当前结果和接下来想做的事，不列普适经验清单。

同时延续 chius.cc 现有文章的个人语气，例如“反复横跳”“蹦迪”“神秘问题”一类自然表达。

## 叙事顺序

正文按真实排查顺序组织：

1. 看到整套设备接近 200W，决定先关机器找基线。
2. 关闭 Jupiter 后，Sol、光猫、AP 和 Saturn 占 UPS 约 17%；打开 Mars 后读数明显上涨。
3. 在 Mars 上处理 CPU EPP、RTX 4060 Runtime PM 和内屏背光，并补上持久化 unit。
4. 关闭 Jupiter 全部来宾测宿主机，再逐个启动 VM/LXC，发现硬件本身有不低的功耗下限。
5. 重启 Jupiter 后 UPS 冲到 50%–60%，先怀疑残留脚本，后来确认是全部来宾同时启动。
6. 记录 duo 的 vCPU 唤醒异常、EVE-NG 一度占满 8 核，以及 UPS 数据的刷新延迟。
7. 收尾写联合重启后的读数如何从 60% 回落到约 31%，以及下一步准备调整重型来宾的 `onboot`。

## 保留内容

- Mars 和 Jupiter 两份已经修正排序关系的 systemd unit。
- `powersave + balance_power`、GPU `auto/suspended` 等实际检查命令。
- UPS 标称 390W、约 30 秒刷新间隔，以及 UPS 是整套功耗而 RAPL 只是 CPU Package 的必要说明。
- 17%–18%、31%–34%、60%、CPU Package 约 6.1W/12W/31W/22W 等实际测量数据。
- Windows、duo、EVE-NG 三个与功耗结论直接相关的来宾名称。

## 删除或收缩的内容

- 删除年耗电量推算和独立数学公式。
- 删除“先建立基线、一次改变一个变量、最后重启验证”式开场总结。
- 删除工整的结果表，把数字放回对应排查过程。
- 删除六条经验总结，不换成另一组同样整齐的列表。
- 收缩对 CPU governor、Runtime PM、RAPL 的教科书式解释，只保留防止误解所需的句子。
- 减少加粗、定义句、过渡总结和面对所有读者的建议。

## 语言约束

- 以“我”作为主要叙述者，优先写“我看到什么、猜了什么、做了什么”。
- 避免“这说明”“由此可见”“更合理的做法”“综上所述”“值得注意的是”等总结腔。
- 不使用“首先、其次、最后”串联整篇文章。
- 不为了完整而重复同一测量口径；UPS 与 RAPL 的区别说明一次即可。
- 不模仿参考作者的具体句子，不把文章写成另一位作者的仿作。

## 技术与披露边界

- 不出现家庭内网 IP、SSH 配置、凭据或完整 VM/LXC 清单。
- 两份 unit 不包含 `After=multi-user.target`，并保留 `WantedBy=multi-user.target`。
- 不把 `no_turbo=1` 写成通用配置。
- 不声称 UPS 可以精确拆分每个来宾的瓦数。
- Mars 修正版 unit 尚待主机恢复在线后部署；正文记录此前重启验证的节能效果，最终发布验收仍需使线上 unit 与文章一致。

- 连续三句以上不使用相同句型列举结论。
